# 有界创作、独立评审与阶段门禁

本流程服务当前片型与 owner 意图。主笔负责创作与取舍，独立评审提供有限、证据化的问题，主代理是唯一调度者和状态写手。主代理可兼任主笔，三个评审任务按维度复用，不每轮新建代理；并发不足时分批独立评审。缺少独立子代理能力就如实降级，不能伪造 reviewer。流程守卫验证记录的一致性与额度；它不是文学评分器、图像审美模型或审批身份验证服务。

## 一次剧本阶段怎么运行

1. 读取 owner 原话、当前全文、已有批准、原始产品资料和必要参考；记录片型、目标时长、表达目标及锁定事实。已明确事项直接沿用，不重复问。已有批准必须确实适用于当前内容，不能把“继续讨论”解释为进入制作授权。
2. 必要时做一次定向研究：围绕当下阻塞创作的一至三个问题，查必要事实或理解明确参考。记录来源、所得事实和仍未知项后回到写作。不为改一句对白重新启动研究，不把无法查看的参考声称看过。
3. 主笔产出初稿。默认最多三份实质候选：初稿加两次修订。把实际源稿注册为候选，守卫保存全文快照及 SHA-256。同周期的同一内容不能反复注册为“新稿”。
4. 首次同时委派三名独立评审：结构与观众（`structure`）、人物与对白（`character`）、品牌与可制作性（`brand`）。每人独立读取当前候选**全文**、owner 意图与锁定事实；不要只给主笔摘要、主笔评分或要求替主笔签字。子代理只返回评审，不能改稿或写流程状态。
5. 每位评审最多三条实质问题。每条包含稳定问题 ID、位置、原文/可见事实证据、影响、最小修复建议，以及 `hard` / `blocking` / `preference`。同一问题跨候选保持同一 ID，禁止改名逃避重复问题停止规则。没有实质问题就返回空列表；不能为了交差凑够三条。
6. 主代理合并问题、辨别矛盾，决定最小修改范围。偏好不是阻塞；硬约束失败不能被平均分抵消。不设置自造的“80 分 pass”，也不把三名评审的不同口味相加成质量承诺。逐步用 owner 已认可/否定的真实样本校准尺度。
7. 首次三审后，局部返修只让相关维度复审，再做一次对新候选全文的必要独立通读（`final`）。各次评审绑定新候选 hash；旧稿的无关维度判断不伪装成已评过新 hash。最终通读者可来自已有独立评审，但不能是该候选主笔。
8. 硬约束和必要独立评审全部通过即停止自动改稿，交 owner gate。未通过则在额度内修订；重复实质问题、退步、来回反复、第三候选仍未通过均停止。保留最佳候选、其全文、未解决问题与停止原因，不强迫把最新稿当最好，也不把停止写成通过。

### 质量观察点

| 维度 | 针对剧情与产品结合短片的观察 |
| --- | --- |
| 结构与观众 | 开场是否有具体可感的吸引；人物动机与因果是否清楚；信息释放、起伏与留白是否适配片型；结尾是否回应表达目标。氛围片、产品演示不强加戏剧冲突，不给反转或爆点设配额。 |
| 人物与对白 | 行为是否有关系和处境依据；对白是否有潜台词、行动意图与人物差异；是否解释已看见的事情；沉默与反应是否更准确。 |
| 品牌与可制作性 | 产品是否参与人物的选择而非突然硬植入；卖点有无事实依据、能否被看见；角色/物件/空间是否可保持；动作、实际台词、停顿能否容纳于目标时长。 |

所有评审都需记录适用硬约束，例如 owner 禁止事项、锁定关系、已批准结尾、可证实产品能力和目标时长。没有某种约束可写明确“不适用”及依据，不能用一条空泛“全部通过”替代核对。

## 局部变更与最佳候选

主代理在修订前记录：基于哪个候选、具体改动、需复审维度、锁定事实核对、改变了哪些事实、下游受影响部分。脚本只要求这些记录存在，不判断“换一句话”究竟是不是改了人物关系或产品承诺。若改动事实、动机、伏笔或结尾，应按真实依赖扩大复审并遵循已有 owner 授权；无关段落和已通过资产保持冻结。

`decide` 的 `comparison` 由主代理依据评审判断：初稿 `initial`，后续 `improved` / `equivalent` / `regressed` / `oscillating`。相当的新稿不覆盖原最佳；若相当的新稿通过而当前最佳并未通过，守卫拒绝这一矛盾裁决并保留 `reviewing` 状态，须核实且确有进步时改判 `improved`；退步/反复立即停止；任何通过仍须独立评审齐全且没有硬约束失败。最佳候选保存在状态的 `script.best_id`，完整文本在对应 `content` 字段。源文件后来被覆盖不改变该快照；交付和批准必须对应选定快照，必要时恢复它再导出。

这是一轮有界自动创作，不是可反复重置的计分游戏。owner 后续提出真实的新修改请求时，用 `owner_change` 开启本次有限周期，记录消息引用、原话、局部范围、受影响批次和下游影响判断。每周期仍至多三候选；总候选 ID 持续递增，旧候选、旧批准、停止原因、实际调用和图片额度全部保留。首次局部修改也只按相关维度加 `final` 复审，不强迫全剧重做三审。没有 owner 新要求不能自行调用此入口；不能删除状态、换 Goal、换主笔、改问题 ID 或新建同类批次偷偷补一轮。

若 owner 明确要求恢复前周期旧稿，默认改剧本分支可在新周期登记该历史内容一次：`candidate` 记录 `reused_from` 来源候选，仍需本周期相关复审和适用批准；不得直接复用旧评审。去重限于当前周期，恢复旧稿不清零调用或图像额度，也不要求故意改字骗过 hash。自动代理仍不得自行开新周期来回换稿。

局部变更使用 `affected_items`，例如 `{"资产批次":["父亲手机"]}`，只让指定项目进入重新评审，其余项目的状态、hash 和评审保持冻结。确实整批受影响时才用兼容入口 `affected_batches:["资产批次"]`；同一批次不能同时写入两项。无下游变化明确传 `affected_items:{}`。`downstream_check` 记录为什么这些项目受影响、其他项目不受影响；脚本不替代语义判断。

**纯下游变更**使用 `owner_change` 的 `script_unchanged:true`，并在 `scope.script_unchanged_reason` 具体说明剧本为何不受影响，`scope.dimensions` 可为空列表。前提是当前剧本已经 `owner_approved`，且实际文件 hash 仍与批准一致。此分支只记录真实新请求、失效指定下游项目，保留剧本状态、批准、周期、候选与全文，可直接独立重审指定资产，不必为资产要求编造一处剧本修改。脚本只校验 hash 与记录，语义上是否真不影响剧本由主代理负责。省略或设为 `false` 则使用原有的剧本改稿分支；实际剧本已改写不能用 `true` 绕过批准。

已通过的受影响图片先转为 `awaiting_visual_review`，旧评审保存在本次尝试的 `prior_reviews`，独立评审可按新设定重看已有图，不消耗生成或修复额度。提示词同理进入 `awaiting_prompt_review`；正文未变可重审，实际文件已改则用 `prompt` 注册新内容候选，再评审新 hash，不能拿旧 hash 通过。只有评审确实发现需要修改时才修复。图像与提示词尝试额度不因 owner_change 自动清零；不足时报告已用额度与阻塞原因，不用换名称绕过。

改写实际剧本后，完成适用检查并记录覆盖改后内容的 owner 批准才推进下游。如果 owner 新消息已明确指定准确改法并授权继续，可将同一真实消息登记为对改后内容的适用批准，无需再询问；只有已有授权不能覆盖改后内容时才等待新的 owner 决策。

## owner gate 与 Goal 接力

内部 `internal_pass` 只表示内部评审通过。资产入口要求 `owner_approved`：主代理从真实对话中记录适用的 owner 批准原话、消息引用、候选 ID 和 hash。没有批准则交付当前剧本与实际结论，在 gate 结束本次工作；不等待空转、不擅自设置 Goal 为 paused，不把 owner 的沉默当同意。

已有 owner 明确批准的旧项目可用 `adopt_approved` 接入：读取现有稿、计算 hash，并记录真实批准原话、消息引用与作者/来源。不强制重做三审，状态明确标记 `existing_owner_approval`，内部 `decision.pass` 为未知而非伪造通过。这个入口只用于空的初始流程，不能覆盖已有候选。后续入口会核对实际选定剧本文件的 hash；改写文件后不能继续使用旧批准。

只有用户明确要求使用 Goal 时才创建宿主 Goal，预算也仅在用户明确给出时设置。创建时把当前可执行目标写清楚，例如“完成限额内剧本候选、独立评审与交付，到 owner gate 为止”。完成这个目标后才可标 complete；不要把覆盖全片制作的既有 Goal 偷换为较小范围或在未实现时标 complete。达到限额未通过也要交付真实停止结果，不能谎报剧本 pass。更大目标若仍需 owner 输入，应在交付中指出，遵守宿主 Goal 状态规则。

owner 后续批准后，再按授权进入下一阶段或创建下一段 Goal；每段 Goal 都加载同一个 `临时工作/流程状态.json`，登记新 Goal ID，但不清零任何候选、调用、图片修复计数。需要跨 Goal 保留的只有事实状态与计数，不启动后台服务。没有获得未来监控请求时不创建定时唤醒。

Goal 标识取宿主实际返回的唯一 ID；若宿主只返回 `threadId` 和 `createdAt`，用二者组合登记同一目标，不单用线程 ID 代替所有阶段，也不捏造宿主未返回的 ID。

只记录实际调用：子代理/研究/工具调用由主代理按真实结果登记 `call`，图像由 `image_result` 自动登记。`review` 记录本身不等于一次调用，重读同一结果不得重复计数。宿主能提供真实累计 token 时用 `usage` 登记每个 Goal 的累计值与来源；无法测量则未知。已测目标的 token 小计不代表含未测目标的总用量。不要写死 token 单价、估计硬预算或假装能从调用次数推出 token。实际预算不足时留出最终复审和交付，不为用完预算增加回合。

## 图片与 prompt-only 分支

- 资产和分镜各登记一个完整批次，列出本阶段全部必需项目；项目命名和是否必需由主代理负责，不能拆批或改名扩大额度。每批 N 项共享 `ceil(N/2)` 次额外生成，每项初始图之后最多修复两次；先达到者为准。已有选图可登记为初始图，不计实际生成调用。资产全部视觉通过后才可建立/处理分镜；确实没有必需资产时先用 `no_assets` 记录具体依据，已有资产批次不能用这项声明跳过。
- 生成前执行 `image_reserve`，成功预约后才调用图像工具；返回后执行 `image_result`。工具失败也如实登记 `called: true` 与失败引用，无图不传 `file`。尚未发出工具调用则 `called: false`。预约是保守额度，一经预约不退还，实际调用数只对 `called: true` 增加；不要把预约数报告成实际调用数。
- 选用图必须在项目内有实际文件。独立视觉评审者逐张、逐视角实际打开图，对照已批准设定和必要参考，核对身份、数量、服装、物件结构、接触、空间及镜间状态；记录图片 hash、实际查看证据、硬约束及最多三条问题。没有图、未查看、主笔自审、hash 不符都不能成为 `visual_pass`。同名文件被覆盖后原视觉通过不能用于视频门禁。
- 修复后仍未通过而额度耗尽，保留结果与原因，停止该项自动出图。整批只有全部必需项目通过才为 `visual_pass`；不能把“生成成功”视作“看图通过”。
- 分镜可选独立的 `prompt_only` 批次。注册提示词全文后独立检查可执行性和连续性，得到 `prompt_only_pass`，对 owner 明确“提示词通过，画面未验证”。此状态允许继续视频提示词，不等待 TapNow 回传；它永远不是 `visual_pass`。评审及视频门禁核对当前提示词文件 hash，不能在文件改写后沿用旧 pass。资产图使用真实看图分支；缺图时如实交付阻塞或待执行说明，不虚构资产验收。

## 宿主具体调用

守卫只依赖 Python 标准库，使用 `-B`，所有状态写在项目下。源稿、图片和事件 JSON 也留在项目，禁止把演练输出写进 skill。有宿主 `load_workspace_dependencies` 时先读取已有运行时路径，否则探测已有 Python 和项目临时目录；不安装框架。以下路径均为占位示意，须换成当前宿主的真实路径。

PowerShell CLI（事件文件由主代理正常写入 UTF-8 JSON）：

```powershell
$guardScript = '<技能目录>\scripts\流程守卫.py'
$pythonRuntime = '<已有Python绝对路径>'
$projectRoot = '<项目目录>'
& $pythonRuntime -B -X utf8 $guardScript $projectRoot init --event "$projectRoot\临时工作\初始化.json"
& $pythonRuntime -B -X utf8 $guardScript $projectRoot apply --event "$projectRoot\临时工作\本次事件.json"
& $pythonRuntime -B -X utf8 $guardScript $projectRoot status
```

`init` 事件为 `{"locked_facts":["父亲与女儿的关系保持不变"]}`；已存在状态时拒绝重建。`apply` 成功后输出紧凑摘要，拒绝返回退出码 2，不改变原状态。摘要只含阶段/额度、项目状态、尝试数和当前文件 path/hash 等必要字段，不回显提示词全文或历史评审。完整证据保存在状态 JSON 中，按需定位读取；Python API 内部可使用返回的完整状态，但给宿主工具回显时使用 `summary()`，不要反复打印完整状态。一次只写一个事件，不并发调用；只有主代理可通过守卫写入。

| --- | --- |

| `usage` | `goal_id`, 非负整数 `tokens`, `source`；真实累计读数，同 Goal 不允许倒退。 |
| `candidate` | `file`, `author`, `hard_checks`；修订另带 `base` 和 `scope`；返回 `c1`/`c2`/`c3` 及 hash。 |
| `review` | `candidate`, `dimension`, `hash`, `reviewer`, `independent:true`, `full_read:true`, `read_evidence`, `issues`, `hard_checks`；所有剧本评审都需独立读全文。 |
| `decide` | `candidate`, `comparison`, `rationale`；脚本依硬约束和评审事实决定状态，不能传自定 pass。 |

| `owner_change` | `requested:true`, `message_ref`, `quote`, `scope`, `affected_items:{批次ID:[项目名…]}`, `downstream_check`；整批变化可用 `affected_batches:[批次ID…]`。可选 `script_unchanged:true` 保留已批准且 hash 未变的剧本，此时 scope 还需 `script_unchanged_reason`；默认 false 开启新的有限剧本周期。 |

| `batch` | `id`, `kind:"assets"/"storyboard"`, `mode:"images"/"prompt_only"`, `items:[名称…]`；同阶段仅一批。 |
| `image_reserve` | `batch`, `item`, `author`；成功后才发出本次生成调用。 |

| `image_existing` | `batch`, `item`, `author`, `file`；仅作为初始选图，仍需独立看图。 |
| `visual_review` | `batch`, `item`, `hash`, `reviewer`, `independent:true`, `viewed:true`, `read_evidence`, `issues`, `hard_checks`。 |
| `prompt` | `batch`, `item`, `author`, `file`；仅 prompt-only，保留全文与 hash；重审期间文件实际变化时用此入口登记新候选。 |
| `prompt_review` | `batch`, `item`, `hash`, `reviewer`, `independent:true`, `read_evidence`, `issues`, `hard_checks`。 |

Python API 与 CLI 共用同一实现；适合宿主把已收到的结构化评审直接送入，不必手工拼接命令行 JSON：

```python
import importlib.util
spec = importlib.util.spec_from_file_location("workflow_guard", r"<技能目录>\scripts\流程守卫.py")
module = importlib.util.module_from_spec(spec)
spec.loader.exec_module(module)
guard = module.Guard(r"<项目目录>")
```
